# 求职场景扩展设计规范（校招 + 社招）

> 状态：已确认的开发基线
> 日期：2026-10-14
> 范围：在保持校招/实习体验不变的前提下，引入"求职场景"维度，覆盖 AI 生成提示词、机会信息库、应用内 Agent、设置与引导。投递阶段扩展（薪资谈判、背调）、社招示例数据链路和 Offer 比较属于后续迭代，不在本规范内。

## 1. 目标

录阶当前以校招/实习场景为主：AI 面试官人设面向"国内大学生实习与校招"，机会信息只覆盖校招数据快照，示例数据与首次引导均为校招视角。本规范引入**求职场景（Career Scene）**作为一等概念，使同一套简历、JD 匹配、面试、投递跟进流程能够同时服务：

- **campus（校招/实习）**：应届生、实习生，关注基础能力、潜力、实习时长与毕业时间；
- **experienced（社招）**：有工作经验的求职者，关注业绩量化、职责边界、职级晋升、离职动机、在职状态与到岗周期。

## 2. 已确认的核心规则

1. 求职场景存储在本地 Settings 单例中，字段 `careerScene`，取值 `campus | experienced`，默认 `campus`。老用户升级后零感知。
2. 场景只决定"表达与侧重"（AI 人设、考察重点、机会检索频道、引导文案），**不**改变业务数据结构：Job、Application、Resume、面试资料、模拟面试的 schema 保持场景无关。
3. 工作年限、期望薪资等候选人事实继续保存在简历（PersonalInfo.yearsOfExperience、简历正文）中，不在设置里重复建档。
4. 所有 AI 任务的输出 schema 不变，场景只影响提示词内容；下游渲染、导出与资料库不受影响。
5. 机会信息库升级为双频道：校招频道保持现状，社招频道为新增数据集；`/api/campus` 路由路径保留，通过 `channel` 参数区分。
6. 社招机会数据是只读参考快照，时效性弱于校招公告聚合，必须标注数据时点并提示以招聘方官方信息为准；不自动创建岗位或投递卡片。
7. 应用内 Agent 的机会检索工具按场景感知：社招场景优先检索 `channel=social`，业务写入仍全部走既有审批边界。

## 3. 求职场景设置

### 3.1 存储

- Prisma `Settings` 新增 `careerScene String @default("campus")`；SQLite 加带默认值字段，无数据回填。
- repository 提供 `getCareerScene()` 与 `updateCareerScene()`；新路由 `/api/settings/career-scene` 提供 GET / PATCH。
- 设置页新增"求职场景"区块：单选"校招 / 实习"与"社招（在职或跳槽）"，保存后即时生效，并说明影响范围（AI 建议侧重、机会库默认频道、Agent 检索）。

### 3.2 传播方式

场景不进入 `EffectiveAiSettings`（它只描述模型连接），由各 AI API 路由与 Agent 会话创建时单独读取，作为独立参数传给提示词构造函数。这样 AI 配置测试、密钥加密等既有逻辑不受影响。

## 4. AI 提示词场景化

统一在 `src/lib/ai/career-scene.ts` 维护场景提示词片段：场景类型、面试官人设、考察重点、HR/招呼语要素等。各任务按场景注入：

| 任务 | campus（保持现状） | experienced（新增） |
| --- | --- | --- |
| 模拟面试出题 | 面向国内大学生实习与校招的面试官；HR 题问"选择实习/校招机会最看重哪些因素" | 面向有工作经验候选人的社招面试官：深挖职责边界、业绩量化与归因、职级晋升逻辑、跨团队影响、离职动机与稳定性；HR 题覆盖离职原因、求职动机、期望薪资沟通、职业连续性 |
| 模拟面试 fallback 题目 | 现有校招题 | 社招版综合/项目/行为/HR 四组题目 |
| 面试复盘教练 | 校招面试教练 | 社招面试教练：关注经历与目标职级的匹配、表述是否体现 owner 意识与业务结果 |
| 面试准备资料 | 现状 | 社招视角：组织与团队背景、岗位在业务中的位置、薪酬与职级谈判准备点 |
| 招呼语 | 第一句要素：到岗时间、可实习时长、每周天数、毕业时间/地点 | 第一句要素：当前在职状态、离职/交接周期、最快到岗时间；强调与 JD 的年限和业绩匹配，不写校园要素 |
| 求职信 | 现状 | 社招语气：以连续职业经历与业绩证据支撑匹配度，避免学生腔 |
| 简历诊断/优化 | 现状 | 社招视角：业绩量化、职责边界表述、空窗期处理、职级晋升证据 |
| 从经历创建简历 | 现状 | 社招叙述重点：按职业阶段组织工作经历，突出晋升与业绩 |

事实边界规则（不编造经历、不提升事实强度、JD 无证据要求不得写成已具备）对两个场景同等适用。

## 5. 机会信息来源（范围外）

调研结论：中国社招市场没有稳定免费的岗位聚合 API——BOSS 直聘、猎聘、拉勾均无公开接口；Indeed 公开 API 已停止；Adzuna 免费层对中国覆盖极差；Greenhouse/Lever/Ashby 的公开 board API 免费稳定但仅覆盖使用该 ATS 的公司，覆盖率不足以支撑“社招机会库”。

因此本轮不做机会库双频道扩展：

- 机会信息库保持校招专版：`data/campus/current.json`、查询 schema、UI、导航命名（“校招信息库”）与 `/api/campus` 全部不变。
- 不发布社招示例快照，不引入任何外部招聘数据依赖。
- 社招用户的机会获取路径是产品主流程：粘贴 JD → 岗位匹配 → 定制简历 → 面试准备；Agent 在社招场景下会明确说明目录仅覆盖校招/实习，并引导走 JD 匹配流程。
- 未来若出现可靠数据源，再按“多数据集 + channel 维度”另行立项。

## 6. 应用内 Agent

- 检索工具保持 `search_campus` 与校招目录不变。
- 系统指令（instructions）按场景生成：说明当前求职场景；campus 场景维持现有机会检索规则；experienced 场景下说明目录仅覆盖校招/实习，社招岗位应引导用户提供完整 JD 走既有岗位定制与面试准备工作流。
- 既有安全与引导规则不变：机会记录只读，检索与查看不得创建 Job/Application，业务写入仍需用户在既有审批卡片上确认；读取 recordId 后再描述详情、标注 asOf 与 deadlineStatus、保留 reviewNote 限定语、声明官方公告优先、目录内容视为不可信数据。

## 7. 引导与文案

- 设置页“求职场景”说明与首次引导文案同步双语（zh-CN / en）。
- “校招信息库”命名、导航与首次引导步骤保持不变。
- 示例数据本轮保持校招链路不变；社招完整示例链路（有工作经验的示例人物、岗位与生成资料）列入后续迭代。
